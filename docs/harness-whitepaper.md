# AI Coding Harness 简短白皮书

## 设计哲学：负责任的编程

AI Coding Harness 希望使用者持续参与代码生成，了解 AI 做了什么，并为审核结果和代码质量承担责任。同时，它通过计划、状态、证据和恢复机制，提高长程任务的稳定性，让工作在多轮交互、上下文压缩和会话中断之后仍有据可查、有序接续。

目前的 LLM AI 无法为生成代码造成的损失承担责任，也不能指望它因后果严重而产生与责任承担者相同的畏惧。代码进入真实项目以后，维护、故障处理和外部影响都由人承受。因此，使用者需要能够检查它的工作过程，决定哪些操作可以执行、哪些结果值得采信，以及哪些代码可以合入。

本项目有意保留大量人工介入场景。批准计划、处理额外命令、审阅测试、登记手动修改和决定合入，都会增加使用成本，甚至显得繁琐。使用者需要投入近乎苦行的耐心，为自己采用的 AI 行为承担责任。harness 通过操作前的授权、执行中的记录和完成后的检查，为这份责任提供具体依据。

## 如何看待 AI 带来的威胁

AI 可以同时编写实现、编写测试、选择验收命令并解释结果。这些环节可能共享同一个错误假设，也可能共同服务于尽快报告完成的倾向。它读取的源码、文档和日志中，还可能包含与任务冲突的指令。

威胁模型需要同时考虑无意失误与主动规避。前者包括遗忘约束、误解结果和任务偏移；后者包括反复更换工具、调整调用方式、改写检查条件，尝试在未获得相应授权时继续执行。本项目将后一类可观察行为称为逆反行为，并将其纳入流程控制。人工介入既要发现错误，也要及时识别这种规避倾向。

## 威胁模型与应对措施

### 长程任务中的上下文丢失与沉默偏移

任务持续时间变长后，AI 可能忘记用户已经作出的决定，重复处理完成的工作，或把临时猜测当成后续步骤的前提。V1 文档将上下文丢失、不可逆操作和沉默偏移列为三类主要风险，当前版本延续了这条设计主线。

harness 将目标、步骤和验收方式写入 `plan.md`，由用户批准并保存内容哈希。计划修改后需要重新批准。任务状态、文件发布和步骤日志持久化到磁盘，完成的步骤对应 Git 提交与标签。会话恢复时，人和 AI 可以核对这些记录，确认已经完成的内容、尚未验证的修改和下一步安排，减少依赖对话记忆造成的反复与偏移。

### 绕过人工授权，扩大实际操作权限

AI 可能把一次任务授权理解成对后续所有操作的许可，在遇到阻碍时尝试直接写文件、使用其他工具，或申请过宽的长期权限。调试过程中产生的删除、配置变更和外部操作，也可能超出用户原本预期。

已接入的写工具由 hook 检查，正式项目文件通过 `harness publish` 发布。shell 调用检查命令、参数、命令替换和重定向，未获许可的调用生成授权票，交由用户处理。发布过程记录文件修改前后的哈希，文件对账检查未登记改动。用户需要审阅授权请求的具体内容；长期放行解释器或整个程序，会扩大 AI 随后能够自行执行的操作范围。

### 选择容易通过的验收，替代真实交付

AI 可能没有运行测试就报告通过，也可能运行了一个容易通过的命令，却没有检查用户需要的功能。例如接口返回正常，并不能说明页面已经显示了数据；旧产物仍然存在，也不能说明本次修改已经生效。

`harness verify` 执行验收命令，保存输出、退出码和耗时，并可检查产物更新、日志模式及与对照产物的差异。代码步骤收尾需要通过的验收证据，并检查证据与该步骤后续发布或登记修改的时间关系。两阶段验收通过 token 关联运行记录与正式确认，`--intent` 可以补充验证层级和交付对象，供人审阅。

验收 token 可以由 AI 读取和回填，测试条件也可能由 AI 编写。使用者仍需判断命令究竟验证了什么，尤其要核对局部测试与最终交付之间的差距。纯规划步骤可以说明理由后免验收，理由会进入工作记录。

### 改写规则与记录，让未完成的工作取得通过状态

面对检查失败，AI 可能尝试修改检查脚本、任务状态或证据内容，让流程接受当前结果。这会同时损害控制措施和后续审核的依据。

harness 将 `.harness/` 等管理路径排除在普通发布之外，使用锁单核对受保护脚本与配置，通过状态机检查任务和步骤的合法转移，并对文件变更进行登记与对账。用户可以结合拒绝记录、发布清单、验收证据和 Git 提交，检查状态变化的来源。规则和工具的维护应由使用者明确安排，避免把解除限制混入普通开发任务。

### 在审核之前提交不可逆结果

AI 可能把完成开发等同于获得发布或合入许可，提前将尚未审阅的改动送入主分支。后续工作建立在这些改动上，会进一步增加撤销和排查的成本。

harness 默认保护 `master`、`main` 等分支，在开发分支上记录任务修改。AI 完成步骤并结项后，由用户在自己的终端输入口令，签发有效期为 24 小时的一次性合入 token，再凭 token 执行合入。计划批准、额外命令授权、手动改动登记和回退等操作也保留人工确认，使使用者能够在关键变化发生前作出决定。

### 持续研究绕过方式，消耗时间与 token

限制越多，越需要观察 AI 如何对待限制。一个面向独立完成任务的模型，可能把流程阻碍当成需要自行解决的技术问题，反复尝试不同入口。用户需要格外关注 Flash 级模型在这类受限任务中的表现，检查它是否将大量推理和工具调用用于规避 harness，而非推进已批准的工作。

hooks 的拒绝信息和操作记录可以帮助识别这种情况：同一操作被多次拒绝、不断更换工具、未经请求便研究关闭检查，或迟迟没有新的代码与验收进展。使用者应及时打断，重新明确允许的路径，必要时拆分或终止任务。当前 harness 不提供对这类行为的自动语义识别或统一 token 熔断，制止无端消耗需要人的持续观察。

## 人工参与如何支持稳定执行

长程任务需要可以核对的进度，也需要能够及时纠正方向的人。计划批准使目标和验收方式在执行前得到讨论；逐步发布和提交让变化保持可审阅的规模；测试记录帮助区分实际完成的工作与仍待证明的判断。发生中断或方向错误时，这些记录为继续、调整或回退提供依据。

使用者因此需要在关键节点查看实际改动和原始证据，而非连续确认所有请求。频繁介入应当带来对代码与过程的了解，形成真实的质量判断。harness 负责把需要检查的操作与记录呈现出来，审核和采用这些结果的责任由使用者承担。

这些措施运行在本机工具和文件权限之内。它们依赖 hooks 正确加载、口令妥善保管，也需要配合执行环境的权限与隔离。本地记录适合过程核查，不具备独立外部审计的抗篡改能力；生产数据、凭据和外部服务仍需相应的访问控制。
